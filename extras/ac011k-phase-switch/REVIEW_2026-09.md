## Unrequested charging on reconnect: evidence

All incident times below are Europe/Berlin. On 26 September HA recorded a
connection at 21:38:59, charging at 21:39:00 and 3753 W at 21:39:11. The user
pressed Stop at 21:39:16. No phase transition was active. Before connection,
8 A remained released and autostart was enabled. The ESP event log explicitly
records “Just plugged in and allowed charging current > 0 (8A)” and then the
start request. This is evidence of configured autostart reusing permission,
not evidence of a spontaneous phase-controller restart.

Autostart was disabled through HA at 22:21. The direct ESP API confirmed false,
with slot 4 active, zero current and clear-on-disconnect enabled. HA continued
to display its old retained value because of the independent MQTT bug below.
This setting change is the only operational change made during the review;
no firmware was installed and no charge or phase test was triggered.

The candidate makes fresh-install session permission closed by default and
clears restored clear-on-disconnect slots at boot. Low-level starts now check
all active current slots, disconnection, GD faults, phase errors and update
state. Phase restart/retry paths also respect revoked permission. Existing
intentional autostart remains a supported setting: the deployment must verify
that it is off for this installation.

## MQTT state stuck after long uptime

The periodic publisher used a signed-half-range deadline comparison against
the last publication time. A state unchanged for over approximately 24.8 days
could fail to publish when it finally changed. The box had roughly 41 days of
uptime; the accepted autostart command and stale MQTT state match this path.
Unsigned elapsed-time comparison replaces the deadline calculation. Host tests
exercise the actual publication method at normal intervals, 41 days and timer
wrap. It still assumes the publisher is serviced within one full timer wrap.

## Phase/power incident: what can be reconstructed

On 21 September a 4780 W target requested 4830 W, three phases at 7 A.
A Start and an automation Stop occurred during the transition. At 15:59:13,
the controller reported that no fresh raw CP-B confirmation had arrived in
30 seconds. At 15:59:24 an ordinary Start resumed charging in the previous
one-phase mode despite the phase error. A new 5400 W slider request at 16:01:18
triggered a new transition: fresh CP, three-phase marker/profile confirmation,
restart, then physical three-phase verification at 16:02:01.

That is a concrete timeout/recovery sequence consistent with the reported
symptom, although it cannot establish that this was the exact remembered
incident. Why the fresh CP report was missing remains unknown. The candidate
blocks ordinary Start from bypassing a phase error and keeps that error until
a deliberate new transition request. It also updates diagnostic phase currents
on every meter report rather than freezing them after verification. No speculative
GD polling command or relaxed CP threshold was added.

## Discovery migration inventory

HA has 21 existing discovery entities and 12 manual MQTT entities on a second
device identifier. Eight manual entities have working discovery replacements;
four expose unimplemented zero-initialized adapter fields and should be retired
(EVSE error code, contactor error, lock state and DC fault-current state).
Actual GD fault information is exposed separately. Six current/voltage sensors
use supported meter indices; per-phase active power and calibrated temperature
or leakage measurements are not fabricated from unsupported fields.

Private backups contain YAML, discovery payloads, registry metadata, dashboard,
history and event log. The read-only planner maps entities and identifies
consumers. A configuration with only the twelve manual definitions removed is
staged privately. Neither it nor the new discovery payloads has been deployed.
Old firmware deletes unknown discovery object IDs, so firmware comes first.

Consumers include charging/retry scripts and automations, stop notifications,
vehicle-data refresh, buzzer logic, a device-based power action and the car
dashboard. An unrelated template helper is attached to the old MQTT device;
it must be detached or reassigned before that device can be removed. External
meter entities stay separate.

### Remaining automation concern

The existing charge-check/retry automation can issue delayed Stop/Start commands
without checking that the original connection and user permission still apply.
Its button-state trigger also needs protection against restored/unavailable
state transitions. Firmware permission checks do not solve a new explicit Start
sent by an automation. During migration, bind retries to the initiating session,
cancel them on manual Stop/disconnect, and verify traces before enabling them.
Until this is done, disable that retry automation for the reconnect acceptance
test; record its previous enabled state for rollback. This work is pending,
not silently counted as fixed by the firmware.
