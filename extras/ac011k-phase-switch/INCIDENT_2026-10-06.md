# 6 October: 2.76 kW target, three-phase charging

Captured read-only while charging at 18:54 CEST, before asking the owner to
stop. No firmware, charging setting or HA automation was changed. The box still
runs `2.0.12-6a820141`; the September candidate has not been installed.

## Evidence

| Time (Europe/Berlin) | Observation |
|---|---|
| 17:44:19 | Request 3230 W → rounded 3450 W, 1P/15 A. Start 3P→1P transition; send Stop. |
| 17:44:25 | New request 2600 W → rounded 2760 W, 1P/12 A, while transition is pending. |
| 17:44:27 | User Start triggers HA retry automation; allowed current becomes 15 A. Normal current action deferred during transition. |
| 17:44:49 | Phase error 4: no fresh raw CP-B confirmation within 30 seconds. |
| 17:44:52 | HA retry automation calls Stop. |
| 17:45:17 | Same automation calls Start; child trace confirms non-retained MQTT `evse/start_charging`, payload `null`. ESP sends Start at 15 A. |
| 17:45:20 | GD reports charging; HA follows at 17:45:21. |
| 18:54:18 | Direct API: requested 1P, commanded/verified 3P, phase ERROR, target 12 A but applied/external-slot 15 A, pending=true. |

At capture, the internal meter reports 9435 W and 13.9 A on each of three
phases, with approximately 224–227 V. The captured HA history through 18:56
peaks at 9790 W on the external meter and 9609 W internally. This substantiates
the large target violation; these records do not show exactly 11 kW.

Autostart is false. This incident is not the earlier autostart-on reconnect
case, nor is the target absent from the ESP: both 2600 W requested and 2760 W
rounded target are present on the device. HA's “implemented power” label and
slider display the rounded target even while pending/error, not applied power.

## Causal chain and candidate coverage

`process_phase_switch()` writes the initial 15 A transition profile into the
external slot. The subsequent 12 A target is queued. `process_power_manager()`
waits for IDLE before applying it; the CP timeout leaves the old 15 A slot and
three-phase mode in place. The HA automation sees “not charging” and retries.
The running firmware's ordinary low-level Start does not check the phase error,
so it starts in the old mode with that stale limit.

The September candidate already rejects low-level Start in phase ERROR and
keeps that error latched until an explicit new request. A host regression now
also reopens the Start slot with a stale 15 A external limit and GD state 6,
matching this incident: no Start is emitted and the error remains. All four
host tests pass. No additional firmware change was needed to block this
specific restart path; physical acceptance of the candidate remains pending.

The retry automation still needs fault/pending checks and session cancellation
as recorded in the working plan. Blocking unsafe continuation does not solve
the CP timeout itself. There is no raw CP report in the event log between the
Stop request and timeout; the next report (918) arrives only after the retry
Start. The car had already been stopped. This suggests checking how fresh CP
reports are obtained in an already-stopped session, but the log alone cannot
prove whether GD did not transmit or ESP missed a frame. Do not accept an old
CP sample or remove the guard as a shortcut. UART capture/query investigation
and controlled hardware tests are still needed.

Also test target replacement through a successful transition: today's pending
12 A target never reached application because the transition failed. The current
incident does not establish correct behavior for that separate path.
